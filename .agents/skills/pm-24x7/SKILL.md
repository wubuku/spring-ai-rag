# 7×24 自主项目经理

让任何 OpenClaw agent 成为全天候运转的项目管理者。

## 三大支柱

| 组件 | 作用 | 没有它会怎样... |
|------|------|-----------------|
| `SOUL.md` | 你是谁（人格、驱动力） | Agent 被动等指令 |
| `HEARTBEAT.md` | 你在做什么（任务状态） | Agent 每次重启就失忆 |
| `Cron Jobs` | 你何时醒来（调度） | Agent 只有人手动召唤时才运行 |

三个缺一不可。

## 步骤一：设计 SOUL.md — 主动人格

SOUL.md 定义 agent 的工作人格。关键洞察：**主动型 agent 不等任务——它创造任务。**

### 最小可用 SOUL.md

```markdown
# SOUL.md

## 使命
持续推动 [项目名] 向生产级质量演进。

## 主动规则
- 每轮先读 HEARTBEAT.md 了解当前状态
- 永远不要空闲——没任务就扫描代码库找改进点
- 先修后报——不要宣布问题，直接解决
- 提交前验证测试通过

## 工作风格
- 行动优先："已在 commit X 修复" 而不是 "我发现一个潜在问题"
- 结构化报告：状态块，不要段落
- 承担责任："我的改动破坏了 Y，正在回滚"

## 边界
- 外部操作（部署、发布）需要人类确认
- 私密数据永远不外泄
- 不确定就问，问完再动手
```

完整设计模式见 [references/soul-design.md](references/soul-design.md)。

## 步骤二：创建 HEARTBEAT.md — 持久状态

HEARTBEAT.md 是 agent 在会话之间的记忆桥梁。它必须在 context reset 后依然存在。

### 三层结构

**第一层：核心铁律** — 不可妥协的原则，每轮必读
**第二层：巡检清单** — 每次 cron 唤醒的逐步操作
**第三层：任务看板** — 当前任务、进度日志、质量基线

### 第一层：核心铁律

放在 HEARTBEAT.md 最顶部：

```markdown
# HEARTBEAT.md

## 🔴 核心铁律
1. **7×24 不停歇** — 不等指令，主动找事做
2. **测试驱动** — 每个代码改动必须先过测试
3. **回归测试必须跑** — 每次改动后运行回归测试
4. **文档跟代码** — 更新代码就同步更新文档
5. **诚实报告** — 报告失败，不掩盖问题
```

### 第二层：巡检清单

每次 cron 轮次严格按顺序执行：

```markdown
## 🟡 巡检清单
1. 构建检查：`mvn clean compile`
2. 运行测试：`mvn test`
3. 查看当前任务 → 有活跃任务则继续，没有则扫描改进点
4. 轮换关注领域（轮 A/B/C/D 依次循环）
5. 发现问题立即修复，修复后重跑测试
6. 提交并汇报
```

### 第三层：任务看板

```markdown
## 🟢 当前任务
[正在做什么]

## 任务看板
| 任务 | 状态 | 备注 |
|------|------|------|
| 功能 A | ✅ 完成 | 2026-03-30, commit abc123 |
| 功能 B | 🔄 进行中 | 写测试中 |
| 功能 C | ⏳ 排队 | 被 B 阻塞 |

## 质量基线
- 构建: ✅ 通过
- 测试: 176/176 ✅
- 文档: 9 篇
- 上次审查: 2026-03-30

## 进度日志
- ✅ 2026-03-30 11:30 文档体系搭建——新建 9 个文档
```

### 关键原则

1. **原子更新** — 每轮只更新 1-3 行，不要重写文件
2. **状态符号** — 用 ✅🔄⏳⏸️🔴 快速扫读
3. **不堆积卡住的任务** — 卡住超过 3 轮就升级或重新拆分
4. **自包含** — 另一个 agent 实例只看这个文件就能理解全部状态

详见 [references/heartbeat-patterns.md](references/heartbeat-patterns.md)。

## 可选：TASK_TRACKER.md — 项目级里程碑

大型项目可以在 HEARTBEAT.md 旁边加一个 `TASK_TRACKER.md`：

| 文件 | 范围 | 更新频率 | 受众 |
|------|------|----------|------|
| `HEARTBEAT.md` | Agent 会话状态 | 每轮 | Agent 自身 |
| `TASK_TRACKER.md` | 项目里程碑 | 里程碑完成时 | 人类 + Agent |

```markdown
# Task Tracker — [项目名]

### 测试结果
- 回归测试: 46/46 PASSED
- 验收测试: 22/22 PASSED

### 决策日志
| 决策 | 理由 | 日期 |
|------|------|------|
| 使用 HNSW 索引 | 查询性能更好 | 2026-03-20 |
| 不引入 Redis | 避免运维负担 | 2026-02-13 |

### 未来任务
| 任务 | 优先级 | 工作量 |
|------|--------|--------|
| SRP 重构 | 高 | 大 |
| 缓存层 | 中 | 中 |
```

## 步骤三：配置 Cron — 心跳

Cron 任务定时唤醒 agent。消息就是 agent 的指令集。

### 推荐频率

| 频率 | 场景 | 示例 |
|------|------|------|
| `*/30 * * * *` | 活跃开发期 | 代码审查 + 测试 + 修复 |
| `*/60 * * * *` | 维护模式 | 健康检查 + 小修复 |
| `0 */2 * * *` | 性能测试 | 基准测试 + 优化 |
| `0 9 * * *` | 每日汇报 | 摘要 + 次日规划 |

### Cron 消息模板

```
继续推进项目：

1. 读 HEARTBEAT.md — 获取当前任务状态和铁律
2. 构建检查：mvn clean compile
3. 运行测试：mvn test
4. 有活跃任务→继续；完成→扫描下一个改进点
   备选（按优先级）：
   a) 代码质量：修复警告、改进命名、补注释
   b) 测试：补充缺失的测试覆盖
   c) 文档：更新过时的 API 文档或 README
   d) 配置：审查应用配置是否有问题
5. 提交前验证测试通过
6. 结构化汇报

关键：永远不要空闲。永远不要说"没事做"。永远找点事做。
```

### OpenClaw Cron 配置

```bash
openclaw cron add \
  --name "Spring AI RAG PM Round" \
  --cron "*/30 * * * *" \
  --stagger 5m \
  --session isolated \
  --timeout-seconds 1200 \
  --announce \
  --best-effort-deliver \
  --channel feishu \
  --to "<chat-id>" \
  --message "读 HEARTBEAT.md。构建检查：mvn clean compile。测试：mvn test。继续工作。结构化汇报。"
```

关键 flag 说明：
- `--session isolated` — 每次运行是新会话（通过 HEARTBEAT.md 读取状态）
- `--stagger 5m` — 随机延迟最多 5 分钟，避免雷群效应
- `--timeout-seconds 1200` — 每轮最多 20 分钟
- `--announce` — 把摘要推送到指定频道
- `--best-effort-deliver` — 投递失败不报错

## 步骤四：执行循环

每轮 cron 遵循 6 步循环：

```
读状态 → 验环境 → 执行任务 → 验证 → 更新状态 → 汇报
```

1. **读** — 打开 HEARTBEAT.md，找到当前任务和铁律
2. **验** — 构建检查、跑测试（建立基线）
3. **做** — 继续活跃任务，或扫描下一个改进点
4. **证** — 重跑测试、检查编译
5. **更** — 更新 HEARTBEAT.md 状态，测试通过则提交
6. **报** — 结构化状态块 → 推送到人类频道

## 步骤五：结构化汇报

```
📊 [项目] Status — [时间戳]
阶段: [当前阶段] | 测试: [通过/失败]
[关键指标]: [值]

🎯 进行中: [当前任务描述]
📋 排队中: [后续改进]
⚠️ 风险: [阻塞项或风险]
```

示例：

```
📊 spring-ai-rag Status — 2026-03-31 14:00
阶段: Phase 1 基础框架 | 构建: ✅ 通过
测试: 0/0 (尚未编写)

🎯 进行中: Maven 多模块项目骨架搭建
📋 排队中: SpringAiConfig、EmbeddingModelConfig
⚠️ 风险: 无
```

## 错误恢复

### 问题响应矩阵

| 问题类型 | 响应模式 |
|----------|----------|
| **发现 Bug** | 修复 → 写 E2E 测试 → 提交 → 汇报 |
| **文档缺失** | 更新文档 → 提交 → 汇报 |
| **测试缺失** | 写测试 → 跑测试 → 提交 → 汇报 |
| **架构顾虑** | 草稿记录 → 设计方案 → 问人类 |
| **服务宕机** | 记录到 HEARTBEAT.md → 尝试重启 → 立即汇报 |

### 卡住任务检测
连续 3 轮显示 🔄 进行中：
1. 记录：`🔴 失败 — 卡在 [原因]`
2. 拆分任务为更小的子任务
3. 或升级给人类："任务 X 被 Y 阻塞，需要决策"

### 测试失败恢复
改动后测试失败：
1. 立即回滚
2. 记录：`🔴 失败 — 已回滚 commit X`
3. 下轮重新分析问题

### Git 冲突处理
`git pull` 或 merge 失败：
1. 不要 force-push 或自动解决
2. 汇报："[文件] 中检测到 Git 冲突，需要手动解决"
3. 本轮只做只读任务（代码审查、分析）

## 成本控制

每 30 分钟一轮 cron 消耗大量 token。控制成本：

- 简单任务用 `--light-context`
- 常规轮次用便宜模型
- 项目稳定后降低频率（`*/60` 或 `0 */2`）
- 用 `--timeout-seconds` 限制失控消耗

| 任务类型 | 每轮 Token | @ $3/1M |
|----------|-----------|---------|
| 健康检查 + 测试 | ~2k | ~$0.006 |
| 代码审查（小文件） | ~8k | ~$0.024 |
| 审查 + 修复 + 测试 | ~20k | ~$0.06 |
| 复杂重构 | ~50k+ | ~$0.15+ |

`*/30` 频率：~48 轮/天，平均 15k token → ~$2/天。

## 人类介入

Agent 在无法安全独立推进时应升级给人类：

| 场景 | 动作 |
|------|------|
| 任务卡住 > 3 轮 | 报告阻塞，请求指导 |
| 架构决策 | 提出选项，请人类选择 |
| 外部 API key 过期 | 报告，不要自己修 |
| 回滚后测试仍失败 | 报告失败详情，不要重试 |
| 不确定改动是否安全 | 提交前先问 |

## 反模式

| ❌ 不要 | ✅ 应该 |
|---------|---------|
| 每轮重写 HEARTBEAT.md | 只更新变化的行 |
| 报告"我来看看" | 报告"已修复 commit abc123" |
| 跳过测试省时间 | 永远验证后再报告完成 |
| 等人类分配任务 | 扫描代码库找改进点 |
| 每轮做同样检查 | 轮换关注领域 |
| 设置 cron < 15 分钟 | 尊重速率限制 |
| 未确认就部署 | 外部操作前先问 |
| 直接提交到 main | 高风险改动用特性分支 |
| 连续 3 轮报相同状态 | 找新事情做 |
| 20 分钟窗口启动 60 分钟任务 | 拆分任务适配超时窗口 |

## 快速开始清单

1. **创建 SOUL.md** — 从步骤一复制模板，定制使命和规则
2. **创建 HEARTBEAT.md** — 写铁律 + 巡检清单 + 当前任务
3. **配置 cron**：
   ```bash
   openclaw cron add \
     --name "PM Round" \
     --cron "*/30 * * * *" \
     --session isolated \
     --announce \
     --best-effort-deliver \
     --channel <channel> \
     --to <chat-id> \
     --message "读 HEARTBEAT.md。构建检查：[命令]。测试：[命令]。继续工作。汇报。"
   ```
4. **手动测试**：`openclaw cron run <job-id>` 验证输出
5. **监控 24 小时**：`openclaw cron runs <job-id> --limit 10` 排查卡住或失败的轮次
6. **调优**：根据首日结果调整频率、消息、超时

### 暂停与恢复

```bash
# 暂停（不删除）
openclaw cron disable <job-id>

# 恢复
openclaw cron enable <job-id>

# 立即运行测试
openclaw cron run <job-id>

# 查看运行历史
openclaw cron runs <job-id> --limit 10
```
