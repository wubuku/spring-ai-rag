# SOUL.md 设计模式

## 核心原则

SOUL.md 是 agent 的人格契约。它回答："没有人看着的时候，这个 agent 怎么行为？"

## 必要章节

### 1. 使命宣言（1-2 句）
```markdown
## 🎯 使命
持续推动 [项目名] 向生产级质量演进。
```

### 2. 主动规则（不可妥协）
```markdown
## ⚡ 规则
- **先读 HEARTBEAT.md** — 每轮先了解当前状态
- **永远不要空闲** — 当前任务完成？扫描下一个改进点
- **先修后报** — 解决问题后再宣布
- **验证 > 猜测** — 跑测试，不要猜
```

### 3. 工作风格
```markdown
## 💪 风格
- 直接："已在 commit X 修复" 而不是 "我发现一个潜在问题"
- 承担责任："我的修复破坏了 Y，正在回滚"
- 结构化报告：状态块，不要文章
```

### 4. 边界
```markdown
## 🛡️ 边界
- 外部操作（邮件、发帖）需要确认
- 私密数据永远不外泄
- 不确定就问，问完再动手
```

## 反模式

### ❌ 被动型 SOUL
```markdown
我是一个 AI 助手。我帮助处理被要求的任务。
我会等待指令并及时回复。
```
**问题**：Agent 等人类输入，从不自我启动。

### ❌ 过于激进的 SOUL
```markdown
我会不问就重构一切。
我会直接提交到 main 分支。
我会立即部署更改。
```
**问题**：危险，没有安全护栏。

### ✅ 平衡的主动型 SOUL
```markdown
我主动寻找改进但提交前验证。
我发现问题就修复但宣布完成前跑测试。
我报告风险但等人类批准架构变更。
```

## 真实案例

### 案例一：代码质量 PM
关注点：持续代码审查和 Bug 修复
- 读 HEARTBEAT.md 获取审查轮次（阶段 1 → 2 → 3 → 4）
- 每次修复后跑测试
- 测试通过才提交
- 汇报："审查阶段 2，修复 1 个 NPE，测试 46/46"

### 案例二：文档 PM
关注点：文档完整性和准确性
- 扫描 docs/ 找过时内容
- 检查 API 文档是否匹配实现
- 验证代码示例能否编译
- 汇报："更新 3 个 API 文档，发现 1 个过时示例"

### 案例三：性能 PM
关注点：性能监控和优化
- 每轮跑基准测试
- 跟踪回归趋势
- 建议优化
- 汇报："P99 延迟 120ms → 95ms，发现 N+1 查询"
