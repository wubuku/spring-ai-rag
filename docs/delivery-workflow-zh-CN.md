# 规划、实施与验收工作流

> [English](delivery-workflow.md) | [中文](delivery-workflow-zh-CN.md)
>
> 本文是 spring-ai-rag 功能交付的长青工作流。它规定从代码探索、规划、实施、验收到 Git
> 交付的最低标准；具体命令和专项测试仍以[开发者参考](developer-reference-zh-CN.md)、
> [测试指南](testing-guide-zh-CN.md)和[发布清单](release-checklist-zh-CN.md)为准。

## 1. 适用范围与总原则

本工作流适用于会改变生产行为、HTTP/API 契约、数据库 schema、跨模块协作、WebUI 工作流
或运维边界的任务。纯错别字、明确的小型文档修复可以按风险缩减规划篇幅，但不能跳过适用的
验证和 Git 保护规则。

交付按以下顺序推进：

```text
探索代码与长青文档
  -> 冻结范围和验收矩阵
  -> 编写自包含规划
  -> 规划连续 3 轮无修改检查
  -> 实施并持续记录进度
  -> 基本集成验证硬门槛
  -> 实现连续 3 轮无修改检查
  -> 最终验收、文档提升和 Git 交付
```

自动化测试和可重复的程序验证是正确性证据；代码 review 用于发现剩余风险，不能代替测试。
不得把首次人工验收当成发现主路径问题的手段。

## 2. 修改前先形成可执行规划

开始修改生产代码前，先阅读受影响模块、邻近实现、迁移、集成测试和相关长青文档。不要只按
文件名或旧 plan 推断现状；代码、已执行迁移、自动化测试和正式 reference/guide 才是事实源。

复杂任务在 `docs/drafts/` 建立活动 plan。规划必须详细到另一位开发者或 Agent 在会话中断后
可以直接继续实施，同时保持近距离链接，避免复制大段已有文档。读者可以通过一层链接查看命令
或完整 API 参考，但不应为了理解核心方案而连续下钻多层文档。

规划至少应冻结以下内容：

1. 当前基线、问题陈述、目标、非目标和受影响模块；
2. 已核对的代码、schema、API、安全和并发事实，以及对应近距离链接；
3. 对外契约、数据模型、事务边界、失败语义、兼容性和回滚策略；
4. 文件级实施顺序和可独立交付的切片；
5. 一次性设计完成的验收矩阵，包括后端集成、前端 Mock、运行时启动和必要的真实依赖验证；
6. 发布开关、可观测性、成本上限、风险和明确非目标；
7. 进度记录方式、规划检查范围、实现检查范围和完成定义。

规划期间主动完成阻断性决策，不把核心契约留给“实施时再决定”。对非阻断未知项给出推荐默认、
理由和可逆边界；只有现有代码、文档和可用环境都无法诚实回答的领域缺口才保留为待讨论项。
无人值守任务应按最有把握的安全默认持续推进，不因可由现有证据决定的选择暂停等待。使用 plan
工具维护当前会话的执行步骤；活动 plan/progress 保存跨会话的持久上下文。

## 3. 规划的连续三轮检查

规划完成后，在实施前执行固定范围的收敛循环。建议三轮分别聚焦：

1. 需求闭环、自包含性、默认决策和非目标；
2. 代码、数据、API、安全、并发和兼容可行性；
3. 实施顺序、验收矩阵、发布、回滚、恢复和交付风险。

每轮都应按需重新查看代码和相关文档，但检查范围必须有边界。发现内容错误、逻辑矛盾、关键
信息缺失或不可实施的设计时，立即修正规划并把全局计数器重置为 `0`；只有连续三轮完整检查
都没有发现问题、且期间没有修改规划正文，规划才可以进入实施。

每轮向当前任务输出检查时间、范围、发现、处理和结果。发现问题并修改文档的轮次写入 progress
或 plan 的检查日志；无问题轮次只在任务输出中总结，不在三轮之间修改文档。完成 `3/3` 后可以
一次性写入最终检查记录，再重跑文档门禁。

会在实施中自然暴露的行号漂移、措辞或格式细节不触发重置。检查只处理会影响正确性、成本安全、
兼容性、数据一致性或可实施性的实质问题，避免发散式润色造成无限循环。

## 4. 可恢复的实施进度

活动任务必须选择一种持久进度方式：在 plan 末尾追加进度，或维护对应的独立 progress 文档。
每次取得关键进展时，先更新进度，再进入下一阶段。进度记录至少包含：

- 当前分支、基线和适用 worktree；
- 已完成切片及关键设计决策；
- 已运行的验证命令、结果和证据位置；
- 当前检查计数、已知问题、下一步和恢复入口；
- 外部依赖或环境限制，但不得记录密钥。

进度文档是恢复账本，不是稳定架构事实。能力交付后，先将仍有效的内容提升到双语长青文档，
再按 [drafts 生命周期](drafts/README-zh-CN.md)归档 plan/progress。

## 5. 一次性设计验收矩阵

在实现前尽可能一次性确定验收测试，不要等 review 每发现一个问题再零碎补一个测试。测试覆盖随
风险扩展，但共享契约、数据迁移、并发控制和用户工作流优先使用高价值集成或端到端测试。
验收矩阵要标明后端、前端、联合运行时和真实模型各项是否适用；未受影响的端可以标为 `N/A`，
但必须说明依据。共享 API 或静态资源契约变化不能仅因没有直接编辑 WebUI 文件而跳过前端验证。

后端验收应覆盖本次修改经过的真实层次：HTTP/controller、service、repository、Flyway 和
PostgreSQL。单元测试用于快速定位边界，不能替代本任务的端到端集成证据。涉及 API 时至少验证
成功、权限、冲突、幂等/重试和失败状态；涉及 schema 时必须从可处置数据库真实执行迁移。

前端验收至少包括 TypeScript、相关 Vitest、生产构建和核心 Mock Playwright。Playwright 只使用
DOM 可见性与可访问状态、网络请求/响应和自动化断言；不得使用截图作为通过依据。必要时可以用
接口 JSON、日志和数据库只读查询补充证据。

前后端分别通过后，只有跨服务契约、代理、认证、序列化、SSE 或运行时配置仍存在不确定性时，
才启动非 Mock 前后端做联合排查。涉及模型行为、embedding、Tool Calling 或真实 provider
兼容时，使用 `.env` 中的凭据执行有界真实 LLM 冒烟；凭据不可用时明确报告环境缺口，不能让
Mock 结果冒充真实模型验证。

## 6. 实现后的基本硬门槛

任何代码改动进入收敛 review 前，先完成适用的基本集成验证。最低后端门槛为：

```bash
mvn clean compile test-compile
# 本任务相关的 PostgreSQL/HTTP 集成测试
# 使用 postgresql profile 启动服务并验证健康检查
```

最低前端门槛为：

```bash
cd spring-ai-rag-webui
npx tsc -b --pretty false
npm run test:run
npm run build
# 本任务核心 Mock Playwright spec
```

还应运行本任务对应的一键验证脚本、`./scripts/verify-no-pessimistic-locks.sh`、
`./scripts/verify-project-docs.sh` 和 `git diff --check`。具体专项命令见
[测试指南](testing-guide-zh-CN.md)；服务启动方式见
[开发者参考](developer-reference-zh-CN.md)。

命令失败、测试被意外跳过、服务无法启动或关键外部验证未执行，都必须如实保留为失败或限制，
不能通过 review 次数将其转换成“完成”。

## 7. 实现的连续三轮收敛检查

基本硬门槛全部通过后，才执行三轮互不重叠、只读、限定范围的实现检查。推荐范围为：

1. 事务、数据迁移、并发、失败恢复和安全边界；
2. API/前端契约、兼容性、权限、成本和用户主路径；
3. 测试证据、运行时启动、文档、发布、回滚和 Git 交付。

发现本任务范围内影响正确性、成本安全、兼容性或数据一致性的缺陷时，立即修改代码，重跑受影响
测试和全部基本硬门槛，并将实现检查计数重置为 `0`。只有连续三轮没有修改实现，才允许结束。
风格偏好和可选优化不在此阶段扩展；不要在 review 中重新发明验收矩阵，避免“审核、补一个测试、
全量重跑”的无界循环。

实现 review 只是硬门槛之后的剩余风险检查。最终信心必须来自已经执行的自动化断言、真实数据库、
可启动服务、构建产物和必要的运行时证据。

## 8. Git 交付与并发工作区

不得丢弃、覆盖或用 `stash` 隐藏工作区中已有或并发产生的修改。开始和提交前都检查
`git status` 与 diff，理解当前 worktree 的全部变化，并在当前任务指定的自动化交付 worktree
中完整提交它们；除非任务所有者明确要求拆分，否则不要静默遗漏其他协作者留下的修改。

需要推送时按非破坏性顺序执行：

1. 完成本地验证并先创建本地 commit；
2. `git fetch` 后把上游分支以 merge 方式合入，不改写已交付历史；
3. 解决冲突并重跑受影响验证；
4. push 后核对本地 HEAD、上游跟踪分支和 `git status`。

普通人工 PR 可以遵循 [CONTRIBUTING](../CONTRIBUTING-zh-CN.md) 的分支/rebase 约定；上述 merge
顺序专用于要求 Agent 在共享或指定 worktree 中直接完成 commit/push 的任务。push 后应恢复干净；
若其他进程随后继续产生 WIP，不要为追赶“绝对干净”无限提交，只报告最后已推送提交和新出现状态。

## 9. 完成定义

只有以下条件全部满足才能报告完成：

1. 规划和进度可恢复，阻断性决策已经冻结；
2. 适用时，后端 API 与数据行为由本任务相关的高价值集成/E2E 测试覆盖；
3. 后端代码受影响时，`mvn clean compile test-compile` 通过，服务可以使用目标 profile 启动；
4. WebUI 或其共享契约受影响时，前端 TypeScript、测试、生产构建和核心 Mock Playwright
   通过，且没有截图验收；
5. 必要的跨服务或真实 LLM 验证已通过，或明确记录不适用/外部环境限制；
6. 规划检查与实现检查分别达到连续 `3/3`；
7. 行为变化已同步到对应双语长青文档，文档门禁通过；
8. Git 提交与远端同步完成，工作区状态已核对。

最终汇报必须列出实际执行的验证及其结果，不用 review 次数、代码阅读或用户后续手测代替证据。
